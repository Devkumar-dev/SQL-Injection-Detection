Understanding SQL Injection (CWE-89 / OWASP A03:2021)

SQL Injection (SQLi) is a critical security vulnerability where untrusted user input is directly concatenated into a dynamic database query. This enables an attacker to manipulate the query's Abstract Syntax Tree (AST), modifying its execution logic, bypassing authentication, or extracting unauthorized records.

⚡

Root Cause: Code vs. Data Confusion

The vulnerability arises when an application fails to enforce strict boundaries between executable SQL instructions (code) and user-provided variables (data). When raw strings are concatenated, characters like ', ", and -- are interpreted as control syntax by the SQL compiler rather than literal values.

Unsafe Pattern (String Concatenation):
query = "SELECT * FROM users WHERE username = '" + user_input + "'"
🔍

Normal vs. Suspicious Login Behavior

Normal User Behavior

  • Input consists of alphanumeric characters (alice, john_doe) or email format.
  • Query logic remains unaltered: checks for an exact username and password match.
  • Only zero or one user record is retrieved.

Suspicious / Attack Behavior

  • Input contains SQL delimiters ('), operators (OR), and tautologies (1=1).
  • Input contains truncation sequences (--, /*) to discard password checks.
  • WHERE clause evaluates unconditionally to TRUE, returning unexpected records.

Vulnerable Construction vs. Parameterized Mitigation

Comparative analysis of database interaction architectures and defense mechanisms.

Security Dimension Insecure Implementation (Dynamic Concatenation) Secure Implementation (Parameterized Queries) Defense Impact
Query Compilation Query and user input are parsed together as a single raw string. Query template is pre-compiled; parameters are sent separately over the binary protocol. Separates executable code from data boundaries completely.
Special Characters (', ", --) Interpreted as SQL control operators and delimiters. Treated purely as literal character data (string constants). An injected ' OR 1=1 is searched as a literal username, never altering logic.
Password Handling Plaintext or weak unsalted hashes (MD5/SHA1) easily crackable via rainbow tables. Cryptographic PBKDF2:SHA256 with 16-byte random salts per account. Prevents offline dictionary attacks and rainbow table lookups even if database is dumped.
Input Validation Absent or relies on fragile blocklists (easily bypassed with encoding/tricks). Strict allowlist validation (e.g. regex for alphanumeric characters) as defense-in-depth. Reduces unexpected data formats before hitting database layers.
Principle of Least Privilege Application runs with full DB administrator (sa/root) privileges. Database connection is restricted strictly to read/write on required tables. Limits blast radius even if another application flaw exists.
01

Primary Defense

Parameterized Queries / ORMs: Always use prepared statements or reputable ORMs (SQLAlchemy, Hibernate) that natively enforce parameter separation.

02

Secondary Defense

Input Sanitization & Allowlists: Validate length, character sets, and formats on all incoming HTTP parameters.

03

Layered Defense

WAF & Real-Time Detection: Deploy Web Application Firewalls and heuristic logging engines to detect anomalous query patterns before DB execution.
